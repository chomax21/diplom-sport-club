Подробное описание проекта: назначение, технологии, архитектура, функции,
роли и последовательность работы с системой.

- **Инструкция запуска:** [../README.md](../README.md)

## 1. Назначение

Система автоматизирует работу спортивного клуба: ведёт клиентов и тренеров,
расписание групповых тренировок, абонементы, платежи, запись и посещаемость,
а также формирует отчёты для администратора и тренеров.

Проект состоит из двух приложений:

- **backend** — REST API на FastAPI с бизнес-логикой и PostgreSQL;
- **frontend** — адаптивное SPA на Vue 3 с тремя ролевыми интерфейсами.

Основные задачи, которые решает система:

1. Исключить двойную запись и превышение вместимости тренировки.
2. Контролировать действие абонемента и остаток посещений.
3. Автоматически проверять занятость тренера и зала.
4. Вести историю платежей и возвратов.
5. Показывать каждому сотруднику только доступные ему разделы.
6. Давать администратору сводную картину по выручке и посещаемости.

### Границы прототипа

- оплата выполняется демонстрационным mock-провайдером;
- наличные оформляет только администратор;
- уведомления по email и SMS не отправляются;
- удаление пользователя заменено блокировкой входа с сохранением истории;
- система рассчитана на один клуб без филиалов;
- мобильное приложение не разрабатывается, интерфейс адаптирован под браузер.

### Как проходит запрос

1. Пользователь выполняет действие в интерфейсе.
2. TanStack Query вызывает функцию из `src/api` через Axios.
3. Axios добавляет access-токен в заголовок `Authorization`.
4. При ответе 401 клиент один раз обновляет пару токенов и повторяет запрос.
5. FastAPI проверяет токен и роль, затем вызывает сервис.
6. Сервис проверяет бизнес-правила и сохраняет изменения в PostgreSQL.
7. Ответ возвращается в SPA; связанные queries инвалидируются, интерфейс
   обновляется, пользователь видит toast или сообщение об ошибке.

## 4. Роли и доступ

| Роль          | Основные возможности                                                                                                | Ограничения                                                             |
| ------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Клиент        | Дашборд, расписание, запись и отмена, свои абонементы, покупка, свои платежи, профиль                               | Не видит чужие данные, управление справочниками и отчёты недоступны     |
| Тренер        | Дашборд, своё расписание, создание и редактирование своих тренировок, список записавшихся, посещаемость, свой отчёт | Не управляет абонементами и платежами, видит клиентов только для чтения |
| Администратор | Все разделы: пользователи, клиенты, тренеры, залы, виды абонементов, абонементы, платежи, расписание, отчёты        | Нет ограничений по разделам                                             |

Роли задаются при создании пользователя и не меняются в прототипе. Проверка
прав выполняется и в интерфейсе, и на backend: скрытие пункта меню не
является защитой, сервер самостоятельно отклоняет запрос с кодом 403.

## 5. Функциональные модули

### 5.1 Аутентификация и профиль

- регистрация клиента по email и паролю;
- вход по email и паролю;
- access- и refresh-токены;
- восстановление сессии после перезагрузки;
- автоматическое обновление токена при 401;
- выход с очисткой кеша запросов;
- профиль пользователя и смена контактных данных;
- блокировка учётной записи администратором.

Access-токен хранится в памяти, refresh-токен — в `localStorage`. Пароли
хранятся в виде Argon2-хеша. В production требуется собственный `SECRET_KEY`
длиной не менее 32 символов.

### 5.2 Расписание тренировок

- список тренировок с фильтрами по дате, тренеру и залу;
- поиск по названию и пагинация;
- карточка и детальная страница тренировки;
- создание и редактирование тренировок;
- отмена тренировки;
- контроль занятости тренера и зала;
- контроль вместимости тренировки и зала;
- запись клиента и отмена записи;
- список записавшихся для администратора и тренера;
- отметки «посетил» и «неявка».

Администратор может создавать тренировку для любого тренера. Тренер — только
для себя и только на свои занятия. Клиент не видит отменённые тренировки.

### 5.3 Абонементы

- справочник видов абонементов;
- создание, редактирование, отключение и включение видов;
- покупка абонемента клиентом;
- оформление абонемента администратором на выбранного клиента;
- список абонементов клиента и администратора;
- отмена абонемента;
- контроль срока действия и остатка посещений.

Абонемент создаётся со статусом `pending`, после успешной оплаты становится
`active`. Отмена переводит его в `cancelled` и обнуляет остаток посещений.
Неограниченный абонемент хранится с `visits_left = null`.

### 5.4 Платежи и возвраты

- история платежей с фильтрами по статусу и клиенту;
- детали платежа;
- способы оплаты `card`, `online`, `cash`;
- mock-провайдер для демонстрационной оплаты;
- наличные только через администратора;
- возврат успешного платежа;
- автоматическая отмена абонемента после возврата.

Возврат запрещён, если по абонементу уже есть посещения. Возврат переводит
платёж в `refunded`, а связанный абонемент — в `cancelled`.

### 5.5 Клиенты, тренеры, залы и пользователи

- клиенты: список, поиск, пагинация, карточка, редактирование контактов и заметок;
- тренеры: карточки, создание через пользователя, редактирование профиля;
- залы: создание, вместимость, описание, отключение и включение;
- пользователи: список, поиск, фильтр по роли, создание, блокировка и разблокировка;
- связь пользователя с профилем клиента или тренера создаётся автоматически.

### 5.6 Дашборды и отчёты

- клиент: активный абонемент, остаток визитов, срок действия, ближайшая запись;
- тренер: тренировки на сегодня, количество записавшихся, заполняемость;
- администратор: выручка, посещаемость, тренировки, клиенты, ближайшие занятия;
- отчёт по посещаемости: период, тренер, занятия, записи, посещения, неявки;
- отчёт по выручке: период, итоги, разбивка по видам абонементов и дням;
- графики Chart.js и табличные дубли данных;
- пустые состояния и экспорт CSV на клиенте.

Тренер видит только свою посещаемость. Отчёт по выручке доступен только
администратору. Период по умолчанию — последние 30 дней.

## 6. Последовательность работы системы

Общая цепочка процессов:

```text
Администратор: залы → тренеры → виды абонементов → тренировки → контроль
Клиент:        вход → покупка абонемента → выбор тренировки → запись → посещение
Тренер:        расписание → список записавшихся → посещение/неявка → отчёт
```

### 6.1 Подготовка клуба администратором

1. Администратор входит в систему.
2. Создаёт залы и указывает их вместимость.
3. Создаёт пользователей с ролью `trainer`; профиль тренера создаётся автоматически.
4. Настраивает виды абонементов: цену, срок действия и лимит посещений.
5. Создаёт тренировки: тренер, зал, время, вместимость и описание.
6. Проверяет расписание и при необходимости редактирует занятия.
7. Отслеживает записи, платежи и отчёты.

### 6.2 Клиент: от регистрации до посещения

1. Клиент регистрируется или входит в систему.
2. Открывает каталог абонементов и выбирает подходящий вид.
3. Указывает способ оплаты и подтверждает покупку.
4. Backend создаёт абонемент и платёж, mock-провайдер подтверждает оплату,
   абонемент становится активным.
5. Клиент открывает расписание и фильтрует тренировки по дате, тренеру или залу.
6. На детальной странице тренировки нажимает «Записаться».
7. Backend проверяет:
   - тренировка не отменена и ещё не началась;
   - есть свободные места;
   - есть активный абонемент на дату тренировки;
   - остатка посещений достаточно с учётом будущих записей;
   - нет пересечения с другой записью клиента.
8. Запись появляется в карточке тренировки и на дашборде.
9. Тренер после занятия отмечает посещение или неявку.
10. При посещении остаток визитов уменьшается на один; при неявке — нет.
11. Клиент может отменить запись до начала тренировки.

### 6.3 Тренер: проведение тренировки

1. Тренер входит в систему и видит тренировки на сегодня.
2. Создаёт новую тренировку или редактирует существующую.
3. Система не разрешает пересечение по времени с другими тренировками
   тренера или занятиями в том же зале.
4. Тренер открывает карточку тренировки и видит список записавшихся.
5. После занятия отмечает каждого клиента как «посетил» или «неявка».
6. При посещении создаётся запись `Attendance`, а остаток абонемента
   уменьшается. При неявке визит не списывается.
7. Тренер открывает отчёт по посещаемости и видит только свои тренировки.

### 6.4 Администратор: продажа абонемента и возврат

1. Администратор открывает раздел абонементов.
2. Выбирает вид абонемента, клиента и способ оплаты.
3. Для наличных платёж сразу считается успешным и оформляется вручную.
4. Для карты или онлайн-оплаты используется mock-провайдер.
5. Платёж и абонемент появляются в истории.
6. При необходимости администратор открывает детали платежа.
7. Возврат возможен только для успешного платежа и только если по абонементу
   ещё не было посещений.
8. После возврата платёж получает статус `refunded`, абонемент — `cancelled`,
   остаток посещений обнуляется.

### 6.5 Отчёты

1. Администратор или тренер открывает раздел «Отчёты».
2. Выбирает период; по умолчанию — последние 30 дней.
3. Администратор может дополнительно отфильтровать посещаемость по тренеру.
4. Система запрашивает агрегированные данные у API.
5. Интерфейс показывает показатели, график и табличный дубль.
6. Данные можно выгрузить в CSV.

## 7. Состояния и бизнес-правила

### Статусы

| Сущность      | Статусы                                      | Смысл                                     |
| ------------- | -------------------------------------------- | ----------------------------------------- |
| Абонемент     | `pending`, `active`, `expired`, `cancelled`  | Ожидает оплаты, действует, истёк, отменён |
| Запись        | `active`, `cancelled`, `attended`, `no_show` | Активна, отменена, посещена, неявка       |
| Платёж        | `pending`, `succeeded`, `failed`, `refunded` | Ожидает, успешен, ошибка, возврат         |
| Способ оплаты | `card`, `cash`, `online`                     | Карта, наличные, онлайн                   |

### Основные правила

- записаться можно только при действующем абонементе на дату тренировки;
- число активных будущих записей не может превышать остаток посещений;
- нельзя записаться на две пересекающиеся тренировки;
- вместимость тренировки не может превышать вместимость зала;
- тренер и зал не могут быть заняты в одно время;
- нельзя создать тренировку в прошлом;
- отмена тренировки отменяет все активные записи на неё;
- отметка посещения списывает один визит, неявка — не списывает;
- возврат возможен только по успешному платежу и при отсутствии посещений;
- после возврата абонемент отменяется;
- заблокированный пользователь не может войти в систему;
- удаление пользователя в прототипе заменено блокировкой.

### Ошибки API

| Код | Когда возникает                                                          |
| --- | ------------------------------------------------------------------------ |
| 401 | Неверный пароль, истёк или отсутствует access-токен                      |
| 403 | Недостаточно прав или учётная запись заблокирована                       |
| 404 | Объект не найден                                                         |
| 409 | Бизнес-конфликт: нет мест, нет абонемента, пересечение, повторная запись |
| 422 | Ошибка валидации входных данных                                          |
| 502 | Ошибка платёжного провайдера                                             |

Ошибки возвращаются в формате `{"detail": "..."}`.

## 8. Модель данных

| Сущность          | Назначение                                           |
| ----------------- | ---------------------------------------------------- |
| `User`            | Учётная запись: email, пароль, имя, роль, активность |
| `ClientProfile`   | Профиль клиента, связанный с пользователем           |
| `TrainerProfile`  | Профиль тренера: специализация, описание             |
| `MembershipType`  | Вид абонемента: цена, срок, лимит посещений          |
| `Membership`      | Оформленный абонемент клиента                        |
| `Room`            | Зал и его вместимость                                |
| `TrainingSession` | Тренировка: тренер, зал, время, вместимость          |
| `Enrollment`      | Запись клиента на тренировку                         |
| `Attendance`      | Факт посещения и кто его отметил                     |
| `Payment`         | Платёж: сумма, статус, способ, провайдер             |

Основные связи:

- `User` 1:1 `ClientProfile` или `TrainerProfile`;
- `ClientProfile` 1:N `Membership`, `Payment`, `Enrollment`;
- `MembershipType` 1:N `Membership`;
- `TrainerProfile` 1:N `TrainingSession`;
- `Room` 1:N `TrainingSession`;
- `TrainingSession` 1:N `Enrollment`;
- `Enrollment` 1:0..1 `Attendance`;
- `Payment` N:1 `ClientProfile`, 0..1:N `Membership`.

## 9. API

Все прикладные маршруты имеют префикс `/api/v1`. Документация Swagger
доступна по адресу `http://localhost:8000/docs`.

| Группа           | Основные маршруты                                                                                          |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| Авторизация      | `POST /auth/register`, `POST /auth/login`, `POST /auth/token`, `POST /auth/refresh`, `GET /auth/me`        |
| Пользователи     | `GET/POST /users`, `GET/PATCH/DELETE /users/{id}`                                                          |
| Клиенты          | `GET /clients`, `GET /clients/me`, `PATCH /clients/me`, `GET/PATCH /clients/{id}`                          |
| Тренеры          | `GET /trainers`, `GET/PATCH /trainers/me`, `GET/PATCH /trainers/{id}`                                      |
| Виды абонементов | `GET/POST /membership-types`, `GET/PATCH/DELETE /membership-types/{id}`                                    |
| Абонементы       | `GET /memberships`, `GET /memberships/{id}`, `POST /memberships/purchase`, `POST /memberships/{id}/cancel` |
| Залы             | `GET/POST /rooms`, `GET/PATCH/DELETE /rooms/{id}`                                                          |
| Расписание       | `GET/POST /sessions`, `GET/PATCH /sessions/{id}`, `POST /sessions/{id}/cancel`                             |
| Записи           | `GET/POST /sessions/{id}/enrollments`, `GET /enrollments/my`, `DELETE /enrollments/{id}`                   |
| Посещаемость     | `POST /enrollments/{id}/attend`, `POST /enrollments/{id}/no-show`                                          |
| Платежи          | `GET /payments`, `GET /payments/{id}`, `POST /payments/{id}/refund`                                        |
| Отчёты           | `GET /reports/attendance`, `GET /reports/revenue`                                                          |
| Служебное        | `GET /health`                                                                                              |

Особенности контракта:

- пагинация возвращает `{items, total, limit, offset}`;
- даты и время тренировок передаются в ISO 8601 с часовым поясом;
- суммы возвращаются в рублях, валюта задаётся настройкой;
- списки фильтруются query-параметрами `limit`, `offset` и доменными полями.

## 11. Запуск

### Быстрый старт через Docker

```bash
cp .env.example .env
docker compose up -d --build
docker compose exec backend python -m app.seed
```

Сервисы:

- API — http://localhost:8000
- Swagger UI — http://localhost:8000/docs
- PostgreSQL — localhost:5433
- Adminer — `docker compose --profile tools up -d`, затем http://localhost:8080

### Frontend

```bash
cd frontend
npm install
cp .env.example .env
npm run dev
```

Приложение откроется на http://localhost:5173. По умолчанию используется API
`http://localhost:8000/api/v1`.
